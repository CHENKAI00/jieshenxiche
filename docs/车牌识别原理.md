# 车牌识别：原理、开源方案、本项目怎么接

> 结论先说：车牌识别不是「OCR 一下整张图」，标准做法是 **检测车牌 → 透视矫正 → 序列识别 → 规则后处理** 四步。
> 商用云 API（腾讯云/百度/阿里）把这四步封好了按次收费；开源方案（HyperLPR3 / PaddleOCR）可以本地跑，**按次 0 元**。

---

## 一、识别原理

### 1. 传统方法（了解即可）
颜色分割（蓝/绿/黄阈值）+ 边缘检测 + 形态学找矩形 → 字符切分 → 模板匹配 / SVM 分类。
缺点很明显：逆光、倾斜、脏污、双排黄牌、新能源 8 位牌基本会崩，现在只在小场景兜底用。

### 2. 现代两阶段（主流）
```
原图
 ├─ ① 车牌检测 Detection
 │    YOLO 系（HyperLPR3 的 HYDET 就是 YOLOv5/v8 改造）→ 输出
 │    车牌框 bbox + 四角关键点 landmarks
 │
 ├─ ② 矫正 Alignment
 │    按四个角点做透视变换（cv2.getPerspectiveTransform），
 │    把倾斜/俯拍的车牌拉成 480×160 左右的正视图
 │
 ├─ ③ 字符识别 Recognition
 │    CRNN（CNN 提特征 + BiLSTM 建模序列 + CTC 解码）直接输出字符序列，
 │    不需要先切字符；轻量方案 LPRNet 用 STN 矫正 + 小 CNN + CTC，模型仅 ~1.7MB
 │
 └─ ④ 后处理 Post-process
      字符集规则：首位省级汉字（京沪粤…）、第二位发牌机关字母（不含 I/O）、
                  序号位 A-Z0-9、新能源 8 位（D/F 打头或结尾）
      颜色分类：蓝/黄/绿/白/黑（新能源绿牌）
      置信度 + 多候选输出
```

关键点在于：**先把车牌摆正再识别**。不矫正直接喂 CRNN，倾斜 15° 以上准确率断崖式下跌；这也是开源方案比「拿通用 OCR 认整图」强的原因。

### 3. 单阶段端到端
YOLO 直接回归字符位置（检测即识别），速度快但对小字符、密集牌不稳，工业界多是「两阶段 + 规则兜底」。

### 4. 为什么需要「规则后处理」
模型会把 `0` 认成 `O`、`1` 认成 `I`、`5` 认成 `S`。我们后端做了字符位纠偏 + 省级简称/发牌机关白名单校验（`backend/src/utils/plate.js`），
错一个字符会导致查不到会员，所以这一步是必须的，不是锦上添花。

## 二、可以直接用的开源项目

| 项目 | 技术栈 | 特点 | 代价 |
| --- | --- | --- | --- |
| [HyperLPR3](https://github.com/szad670401/HyperLPR) | YOLO 检测(HYDET) + CRNN/CTC，ONNX | 中文车牌专用，蓝/绿/黄/白/黑全支持，Python/C++/ARM/Android/iOS 都有；ARM 上可做到 ~100ms；社区活跃 | 需要 Python 或 ONNX 运行环境；模型文件几十 MB |
| [PaddleOCR 轻量车牌方案](https://paddlepaddle.github.io/PaddleOCR/v2.10.0/ru/applications/%E8%BD%BB%E9%87%8F%E7%BA%A7%E8%BD%A6%E7%89%8C%E8%AF%86%E5%88%AB.html) | PP-OCR 检测(DB) + 识别(SVTR/CRNN) | 通用 OCR 底座微调车牌，中文场景成熟，文档全 | 依赖 paddlepaddle，部署体积大，CPU 推理偏慢 |
| [LPRNet](https://github.com/D-Robotics/rdk_model_zoo/blob/rdk_x5/samples/vision/lprnet/README_cn.md) | STN + CNN + CTC | 极轻量（~1.7MB），端侧/嵌入式友好 | 只做识别，需要自己配检测器；中文省简称要自己训 |
| 传统 OpenCV 模板匹配 | 颜色+形态学+模板 | 零依赖、可解释 | 准确率低，只适合固定机位 |

**本项目的选择**：HyperLPR3。理由是它把「检测+矫正+识别」都封装好了，模型专注中文车牌，且能通过 HTTP 侧车方式接入现有 Node 后端，不动主服务架构。

## 三、本项目怎么接（三种引擎，一个出口）

`backend/src/services/ocr.js` 的 `recognizePlate(buffer)` 是唯一出口，`.env` 里 `OCR_ENGINE` 切引擎：

```ini
OCR_ENGINE=auto          # auto | mock | hyperlpr | tencent
HYPERLPR_URL=http://127.0.0.1:18090
TENCENT_SECRET_ID=       # 只有用腾讯云才需要
TENCENT_SECRET_KEY=
```

| 引擎 | 调用方式 | 成本 | 适用 |
| --- | --- | --- | --- |
| `hyperlpr` | 本地 Python 服务 `POST /recognize {image:base64}` | **0 元/次**，只吃 CPU | 单店/多店自建，隐私不出内网 |
| `tencent` | 腾讯云 LicensePlateOCR（TC3 签名已手写） | 按次计费，有免费额度 | 不想维护模型、追求最高准确率 |
| `mock` | 随机返回演示车牌 | 0 | 开发/演示 |

`auto` 的降级顺序：**本地 HyperLPR → 腾讯云 → mock**，本地服务挂了会记错误并自动换下一个，前台永远能出结果（最差也能手输车牌）。

### 起本地识别服务

```bash
# 服务器上（Python 3.8+）
pip install hyperlpr3 fastapi uvicorn opencv-python-headless   # 或只装 hyperlpr3
nohup python3 scripts/hyperlpr_service.py >> logs/lpr.log 2>&1 &

# 验证
curl -s http://127.0.0.1:18090/health          # {"ok":true,"engine":"hyperlpr3"}

# 后端切过去
sed -i 's/^OCR_ENGINE=.*/OCR_ENGINE=hyperlpr/' .env && bash deploy/manage.sh restart
```

服务只监听 `127.0.0.1:18090`，不对外暴露；Node 侧 5 秒超时 + 失败降级。
`scripts/hyperlpr_service.py` 已经写好，做了 base64 解码、结果归一化（车牌/颜色/置信度/框）、按置信度排序。

### 准确率还能怎么提（工程手段，比换模型更划算）

1. **拍摄引导**：取景框里要求车牌占宽 ≥1/3、水平偏差 ≤15°，前端加辅助线（下一步可以做）
2. **连拍 3 帧投票**：同一辆车连拍，取出现次数最多的车牌，能消掉偶发单帧误识别
3. **双引擎交叉验证**：本地 + 云同时跑，不一致就降级「置信度低，请手输/修正」，把错误挡在入会前
4. **失败样本回收**：`plateValid=false` 的图留一份（脱敏、限存 7 天），用于调阈值或后续微调模型
5. **后处理规则**：省简称白名单 + 发牌机关字母 + 新能源 8 位规则（已实现，见 `utils/plate.js`）

## 四、当前实现的边界

- 小程序端没有本地识别能力，只能拍照上传；单张识别耗时：云 OCR 300–800ms，本地 CPU 100–300ms
- 图片只在内存中处理（`multer memoryStorage`），不落盘；上限 8MB
- 识别失败不会阻断业务：返回 `plateValid:false` + `reason`，前端弹手输面板
- 云端识别按次计费，所以默认 `auto` 且本地服务优先；没有本地服务时自动 mock（开发不烧钱）
